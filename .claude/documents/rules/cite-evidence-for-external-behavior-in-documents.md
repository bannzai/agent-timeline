# 外部サービスの内部挙動を文書に断定形で書く前に、計測・出典・ソース参照を同じ場所に置く

CloudKit・APNs・Keychain・App Store Connect のような外部サービス・フレームワーク・OS の内部挙動と、自分で見ていない画面の表示は、裏付けが無くても断定形で書けてしまう (起票元: https://github.com/bannzai/castle/issues/1198 )。

## 発火する場面

- README・プライバシーポリシー・紹介サイト (LP)・ストア文言 (`fastlane/metadata/`)・`docs/`・`documents/` に、外部サービス・フレームワーク・OS が内部で何をするかを書く時
- OS・フレームワークが描く部分 (記号・アイコン・システムのダイアログの文言・標準のメニュー) を手順に書く時に、その画面を simulator・実機・ブラウザで自分が見ていない時
- 通知の payload・保存されるレコード・外部へ送られる内容の範囲を、プライバシーポリシーや README に書く時

自分のアプリが描く画面・メニュー項目・ボタン名だけを並べた手順 (ユーザーに許可を求める手順を含む) と、自分のコード・スキーマ・コマンドの説明は対象外。

## やること

断定形で書く前に、(a)(b)(c) のどれかを同じ段落か脚注に置く。どれも置けない時は「仮説」「未確認」と書く。

1. **(a) 計測した事実**: 何を実行して何が返ったかを書く。計測が裏付けるのは観測した事実だけで、そこから推定した機序は裏付けない。推定を書きたい時は推定と分けて書く
2. **(b) 一次情報の出典**: documentation の URL と、そこから引いた文を並べる。URL だけを置いて、documentation が書いていないことまで断定しない
3. **(c) 実装のソースの参照**: ファイル名と、そこから読める事実を書く。参照するソースの意味も一次情報で確かめてから書く

利用者向けの文書 (プライバシーポリシー・README・紹介サイト・ストア文言) で本文に出典を書くと読みにくくなる時は同じ箇所の HTML コメント (`<!-- source: <ファイル名>: <そこから読める事実> -->`) か markdown の脚注に置く。裏付けをファイルの外 (PR body・コミットメッセージ・会話) にだけ書くと、文書を読む人にも Jev の検査にも届かない。

Jev の検査 (`~/.agents/skills/jev-check/assets/rules/coding-rules.json` の `cite-evidence-for-external-behavior`) が候補を出した時は、候補の行に (a)(b)(c) を足すか「仮説」「未確認」に書き換える。rule・ガイドが「書いてはいけない例」として断定文を引用している箇所は誤検知なので、直さずに「書いてはいけない例の引用」である旨を commit message か PR body に 1 行書く。

## 既存ルールとの関係

- `~/.claude/CLAUDE.md` 規約の「不明な点は Web で調べてから答える」「未検証の部分は未検証と書く」: 本ルールは、確信していても上記の文書に上記の種類の文を書く時に裏付けを要求する
- `~/.claude/documents/rules/verify-external-cli-cause-with-debug-log.md`: 外部 CLI の挙動を README に書く時は両方が効き、裏取りの方法はあちら、文書に残す裏付けの置き方は本ルールに従う
- `~/.claude/rules/ui-change-screenshot-verification.md`: 見ていない画面をスクリーンショットで撮って確認したなら、その事実が (a) の計測になる
