# Firebase Functions・Firestore のインデックス・Remote Config を確認なしでデプロイしてよい条件

ユーザーがデプロイ権限を持つリポジトリ (owner を問わず、業務委託先を含む) の Firebase Functions・Firestore のインデックス・Remote Config は、dev / prod を問わず、下の基準で「出してよい」に当たる時だけ、ユーザーに確認せずにデプロイしてよい。止める基準は「prod だから」「owner が誰か」ではなく「下位互換が壊れるか」で、それ以外はデプロイせず、判定の根拠とコマンドを示してユーザーに確認する (起票元: https://github.com/bannzai/castle/issues/1346 、owner の限定を外して下位互換の基準にした決定: https://github.com/bannzai/castle/issues/1530 )。

## Firebase Functions: 下位互換の判定

本番では、ストアに残る旧バージョンのアプリと新バージョンのアプリが同時に同じ Functions を使う。デプロイする関数ごとに、その関数の差分と、その関数が import する共通コードの差分を読み、次の 4 点を確かめる (観点の出典: Sukidayo-app/Riamo の `riamo-firebase-deploy-commands-suggest` skill Step 5)。

1. 呼び出しの契約: onCall の入力スキーマと戻り値の形、タスクキューの payload、トリガーが読むドキュメントのフィールド。旧アプリから呼ばれても新アプリから呼ばれても動くか (必須項目の追加・項目の削除・型の変更・エラーの返し方の変更が無いか)
2. データ: 関数が書き込むフィールドの追加・削除・型の変更と、関数が読むフィールドを誰が書くか。新アプリしか書かないフィールドを無い時の扱いを決めずに読んでいないか、旧アプリが読むフィールドを書かなくなっていないか。保存するデータの構造や既存データを変える (マイグレーションを含む)・権限の判定を変える変更はここに当たる
3. 関数の削除・名前の変更: 旧アプリが呼ぶ関数を消す・改名していないか (デプロイ済みの関数を消す・名前を変える変更はここに当たる)
4. 先に必要なもの: Firestore のインデックス・セキュリティルール、シークレット、Remote Config のキー、マスターデータが、関数より先に本番に入っている必要があるか

| 判定 | 条件 | 扱い |
| --- | --- | --- |
| いつでもよい | 1〜4 のどれにも当たらない (新しい関数の追加、本番の不具合の hotfix、文言・ログの修正、影響が無いと確かめた変更等) | デプロイする |
| アプリのリリースより先 | 新アプリが新しい契約・フィールドを使い、関数側は旧アプリとも互換 (足した項目が任意で、旧アプリが送らなくても従来どおり動く等) | デプロイする (アプリをストアに出す前に prod へ出す) |
| 旧アプリが減ってから | 旧アプリが使う契約・フィールド・関数を壊す (1〜3 に当たる) | デプロイせず確認する |
| 別のものを先に | 4 に当たり、先に必要なものがまだ本番に入っていない | デプロイせず確認する (先に出すものと順序を示す) |
| 判定できない | 契約や書き込むフィールドを変えているのに、互換がどう保たれるかを差分と説明から読めない | デプロイせず確認する (「いつでもよい」に倒さない) |

新規の関数は旧アプリから呼ばれないため 1 は見ないが、2〜4 は見る (改名は新規の関数として現れ、旧関数が本番に残るため 3 も見る)。新規と既存が混ざる時は既存の関数の基準で判定する。

### 判定の手順

デプロイの前に、上の基準で「いつでもよい」か「アプリのリリースより先」と自分で判断した上で `~/.claude/scripts/check-functions-deploy-allowed --project <プロジェクト ID> --functions <関数名,...> [--pr <PR 番号> | --base <ref>]` を、デプロイするコードの checkout で実行する。デプロイしてよいのは exit 0 の時だけで、exit 1 (確認に回す)・2 (保留)・3 (Jev が答えられない)・4 (引数・取得のエラー) はどれもデプロイせず、出力の `reason` を添えてユーザーに確認する。互換の保ち方・先に入れたもの・会話で確かめた内容は `--note` で渡す (説明に書かれていない互換の根拠は Jev に見えないため)。オプション・判定に渡す材料・出力の形・判定した差分と実際にデプロイするコードが食い違う時の扱いはスクリプトのヘッダーコメント、判定の条件の写しは `~/.claude/checks/decisions/firebase-functions-deploy.json` を SSOT とする。

## Firestore のインデックス

`firestore.indexes.json` (または firebase.json の `firestore.indexes` が指すファイル) の差分で判定する。インデックスの追加だけ (既存のエントリを消す・変える行が無い) なら確認なしでデプロイしてよい (`firebase deploy --only firestore:indexes`)。削除・変更 (フィールドの並び・順序・クエリスコープを変える) は、そのインデックスを使うクエリが本番で失敗し得るため、デプロイせず確認する。Jev の判定は通さない (追加だけかは差分で確定できる)。

## Remote Config

テンプレートの公開は、ユーザーが公開を指示し、対象のキーと値が指示から特定できる時だけ確認なしで行う (指示された公開は依頼の範囲内で、`~/.claude/CLAUDE.md`「自律性と確認の境界」の「依頼に含まれない外部への書き込み・公開」に当たらない)。A/B テストや段階公開の有効化のように「公開 = ユーザーへの影響の開始」になる変更を agent が自分の判断で行うことは、依頼に含まれない公開として確認する。公開後はテンプレートを再取得し、対象のキー以外に差分が無いことを確かめる。

## 対象外

- Firebase Functions・Firestore のインデックス・Remote Config 以外のデプロイ (Hosting・Firestore / Storage のセキュリティルール・Cloud Run 等) は対象外で、従来どおりユーザーに確認する

ユーザーがデプロイを承認した時は、判定を通さずにデプロイしてよい (承認は `~/.claude/CLAUDE.md`「自律性と確認の境界」のとおりユーザー本人の発言に限る)。

## 既存ルールとの関係

- `~/.claude/CLAUDE.md`「自律性と確認の境界」: 承認の要否の定義は同セクションが SSOT。本ルールは、本番環境への変更として確認していた Firebase Functions・Firestore のインデックス・Remote Config のデプロイのうち、上の基準に当たるものを確認の対象から外す例外の条件だけを定める。PR のマージの承認境界 (owner が bannzai 以外のリポジトリは明示の指示が要る。ADR 0081) は変えない
- Jev は単独の根拠ではなく、agent が本ルールの基準で deploy と判断した上で同意を求める 2 人目の判定役。不一致・保留・Jev 不達はすべて確認に倒れ、Jev の答えでデプロイ側へ動くことは無い (`~/.claude/checks/decisions/README.md`)
- `~/.claude/rules/firebase-environment-check.md`: デプロイ前の対象環境 (`firebase use`・`.firebaserc`) とシークレットの確認は同ルールに従う。本ルールの判定はその確認を省略しない
- デプロイの前提になる PR のマージは `~/.claude/skills/auto-merge-pr/SKILL.md` の手順に従い、本ルールはマージを許可しない
- 対象リポジトリの CLAUDE.md / AGENTS.md・`.claude/settings.json` の `permissions.ask` がデプロイを止める時はそちらが先に効く。本ルールはそれらを緩めない (Riamo 側の同方針の変更: https://github.com/Sukidayo-app/Riamo/issues/1852 )
