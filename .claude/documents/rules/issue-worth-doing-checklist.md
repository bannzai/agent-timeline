# なぜやるか: issue を作る時と着手する時に「やる意味」を 6 つの問いで確かめる

「作業のための作業」を作らない・始めないための検査。issue を生成する側は issue 本文に答えを書き、着手する側は答えを読んで通す。答えられない issue は作らない・着手しない (起票元: https://github.com/bannzai/castle/issues/1293 )。

## 6 つの問い

issue 本文に `## なぜやるか` セクションを置き、次の順で 1 行ずつ答える。番号と問いの文言は変えない (着手側と Jev の検査が同じ文言で照合する)。

1. **どの仮説・指標を動かすか**: プロダクトの方向性の文書 (`documents/DIRECTION.md`。型は `~/.claude/documents/rules/product-direction-document.md`) の判定基準のどの行を動かすか。動かさないなら、やらないと困る理由は何か。困る理由の例: 致命的な不具合、おかしな文言、Apple / Google のアカウント連携はあるのにログイン導線が無いような機能の欠け
2. **何を観測して思いついたか**: 数値 (計測・ストア指標)、クラッシュ、レビュー、失敗したテスト、ユーザーの発言のどれか。観測が無い思いつきはその旨を書く
3. **うまくいったら次に何が変わるか**: 指標の値、ユーザーの行動、次に着手できる issue のどれか
4. **これの最小の版は何か**: 完了条件を満たす最小の変更範囲。issue の完了条件はこの最小の版で書く
5. **今日これ 1 件しか出せないとしても出すか**: 出さないなら、この issue は後回しの候補で、`daily_issue_cap` (下記) の枠を使わない
6. **まともなエンジニアが読んで、やるべきだと納得する理由が書けているか**: 1〜5 を読み返し、理由を 1〜2 文で書く。書けなければ issue を作らない・着手しない

方向性の文書が無いリポジトリ (castle・ツール・業務委託先) では 1 を「どの運用・成果物のどんな問題を解消するか」と読み替える。

## issue を生成する側

- 上限: プロダクトごとに 1 日に生成してよい改善 issue は `documents/DIRECTION.md` の `daily_issue_cap` (既定 3) まで。候補が上限を超える時は列挙せず、問い 5 で「出す」と答えた候補から、問い 1 の指標への効きが大きい順に選抜する。上限に達した日は残りを issue にせず、次の判定 (product-loop skill の次回実行) に持ち越す
- 問い 6 に答えられない候補は issue にしない。「後で必要になるかもしれない」「きれいになる」は理由にならない
- チェックリストの例に無いことでも、やるべき理由 (問い 1 の困る理由) を明確に書けるなら issue にしてよい

## 着手する側

- issue 本文に `## なぜやるか` があれば読み、問い 6 の理由に納得できるか (問い 1〜5 と矛盾しないか) を確かめてから実装に進む。旧見出し `## 意味の門` で書かれた既存の issue も同じに扱う
- 無い issue は、着手する agent が本文とコメントから 6 つの問いに自分で答え、Pull Request 本文の「完了条件」の前に `## なぜやるか` として書く。問い 6 に答えられない時は実装せず、その旨と答えられなかった問いを issue にコメントして止まる
- ユーザーが対話で直接指示した作業は、指示そのものが問い 6 の答えに当たるため、本文の有無で止めない

## チェックリストの更新

問いの追加・文言の変更は本ファイルだけを編集する。入口は improve-instructions-from-history skill Phase 3 と、daily-retrospective skill が「作業者の評価」から起票する castle の issue (同 skill は本ファイルを直接編集しない)。追加した問いは番号を末尾に足し、「納得する理由」の問いを最後に置き直す。

## 既存ルールとの関係

- `~/.claude/documents/rules/write-completion-condition-per-task.md`: 本ルールは「その issue をやる意味」を問い、完了条件は問い 4 の最小の版で書く
- `~/.claude/documents/rules/auto-implement-label-on-issue-create.md`: 本ルールで作らないと決めた候補は label の判断に進まない
