# 実機・マニュアル動作確認はリリース前の一括確認へ後ろ倒しする

実装 issue の完了条件に、実機・配布ビルド・実アカウント・物理デバイスの機能でしか成立しない確認 (実機操作・TestFlight 等の配布ビルドでの人間確認・Sandbox 購入・電話発信、手元でテストを実行して途中の Touch ID / パスワードのプロンプトに人間が答える確認等) が含まれる場合、都度ユーザーに実施を依頼して issue をブロックしない (起票元: https://github.com/bannzai/castle/issues/781 )。準備コストが issue の数だけ発生するため、リリース前に一度でまとめて実施する。

移管先は、その取り組み (初回リリース前なら初回リリース、それ以降は次のリリース) の「ユーザー作業の一覧」issue の `## 実機・実環境での確認` セクション。その issue の見つけ方・新規作成・書式は ~/.claude/documents/rules/record-user-only-tasks-in-single-issue.md を SSOT とする。

人間に回すのは、上の「実機等でしか成立しない確認」だけにする。agent のツールで確認できる項目と、テスト・コードで既に担保されている項目を人間の確認に回すと、人間の手作業を減らすという無人実装の前提に反する (起票元: https://github.com/bannzai/castle/issues/1531 。業務委託先のリポジトリの無人実装で、シミュレータのロケール変更で確認できる 4 言語の表示と、単体テストで担保済みの通知文言を人間に移管した)。

## ルール

### 実装時: 移管する前に項目ごとに 3 択で判定する

agent が完遂できる範囲 (実装・機械検証・配布経路の整備等) を完了させた後、完了条件に残る確認の項目を 1 つずつ次の 3 つに分ける。「自分がまだ確認していない」は「確認できない」ではない。確認に時間がかかることも移管の理由にしない。

1. **agent のツールで確認できる**: シミュレータのロケール・デバイス (小画面機種) の変更、エミュレータ、ブラウザ、API の呼び出し、テストの実行で成立する確認 (例: 多言語の表示の折り返し、小画面でのレイアウト、Slack 通知の文言、バックエンドの生成処理の結果)。agent が確認を完遂するか、確認しないと決めるかのどちらかにし、人間の確認項目にしない
   - 確認する: 完遂する。司令塔の条件を満たすセッションは、`~/.claude/documents/rules/fable-task-orchestration.md`「実行先の判定」に従って作業者に出してよい
   - 確認しない: 価値に対して費用が大きい項目 (例: 1 言語で崩れていない表示を残りの言語でも撮る) は、確認しない理由を PR body の `## やらないこと` セクション (無ければ作る。「セッション再開」より前) に `- <項目>: <確認しない理由>` の形で書いて終える。チェックボックス (`- [ ]`) にしない (未チェックの項目があると自動マージが止まる。commit-create-pr skill「自動マージと未チェックのチェックリスト」)。同じ項目を `## 人間が確認` や「未達の完了条件」にも書かない。完了報告にも同じ内容を書く (`~/.claude/documents/rules/report-undone-scope-in-completion.md`)
2. **テスト・コードで既に担保されている**: 単体テスト・Functions のテスト・コードの分岐で、完了条件の文言・挙動が決まっている項目 (例: gender が null の時に「性別：未設定」を組み立てるテストがある通知文言、バリデータの分岐を削除してテストが通っている生成処理)。実環境での再確認を人間に頼まず、根拠 (テスト名・分岐の場所) を PR body の検証結果に書く
3. **実機・配布ビルド・実アカウント・物理デバイスの機能でしか成立しない**: 物理デバイスの操作、TestFlight やストアの配布ビルドでの確認、Sandbox アカウントでの購入、電話の発信、プッシュ通知の受信、人間が認証プロンプトに答えるテストの完走。この項目だけを下の手順で移管する

人間が認証プロンプトに答えるだけで完走するテスト (例: 削除時に必ず Touch ID / パスワードを求める Secret を扱う `make test-integration`) は 3 に当たり移管の対象にする。未実施でもマージして壊れるものは無く、PR の `## 人間が確認` に置くと自動マージが止まるだけになる (`## 人間が確認` に置いてよい項目は auto-implement-issue skill Phase 4 の手順 6 を SSOT とする)。

判定は、迷うかを問わず、issue の完了条件のセクションだけを切り出して `~/.claude/scripts/jev-decide ~/.claude/checks/decisions/defer-manual-verification.json --decided <defer|none>` で確認する (`defer` = 3 の項目がある、`none` = 1 と 2 だけ)。不一致 (exit 1) は出力の `fallback` に従う。保留 (exit 2) は `fallback` に従わず、項目ごとに上の 1〜3 を判定し直し、3 と言い切れる項目がある時だけ `defer` にする (保留を一律に移管側へ倒すと、agent が確認できる項目まで人間に回る。起票元: https://github.com/bannzai/castle/issues/1531 )。Jev の答えが無い時 (exit 3) は自分の判定のまま進める。

### 実装時: 3 の残項目を「ユーザー作業の一覧」issue の確認のセクションへ移管する

1. 対象リポジトリの open issue から移管先を ~/.claude/documents/rules/record-user-only-tasks-in-single-issue.md「記録する」に従って探す
2. 移管先があれば、先頭に `## 実機・実環境での確認` の見出しを置いた残項目のチェックリスト (`- [ ] 操作手順と期待する結果`) を、その issue への新規コメントとして投稿する。移管先が無ければ同ルール「記録する」の手順で「ユーザー作業の一覧」issue を新規作成し、`## 実機・実環境での確認` セクションにチェックリストを書く (確認に必要な前提 (配布手段・テストアカウント等) も書く)
3. 元 issue に、移管した項目と移管先 issue の URL をコメントで記録する
4. 元 issue を close するかは既存の承認境界 (`~/.claude/CLAUDE.md`「自律性と確認の境界」) に従う。移管の記録があるため、close しても残項目は失われない
5. 完了報告に、移管した項目と移管先 issue の URL を含める

### 起票時: 実機・マニュアル確認を個別 issue の完了条件に入れない

実装 issue を起票する時 (create-new-app skill の MVP ロードマップ子 issue 化を含む) は、上の 3 に当たる確認を個別 issue の完了条件に入れず、「ユーザー作業の一覧」issue の確認のセクション側へ集約する ( https://github.com/bannzai/castle/issues/781 )。人間が認証プロンプトに答えないと完走しないテストもこれに当たる (例: 「`make test-integration` が exit 0」で、その中に削除時に Touch ID / パスワードを求める Secret の項目がある。完了条件には「テストの項目が追加されている」「認証の要らない `make test` が exit 0」のように agent が満たせる範囲を書き、実行は確認のセクションへ回す)。1 と 2 に当たる確認は完了条件に書いてよい (agent が満たす)。

## 既存ルール・skill との関係

- ~/.claude/documents/rules/qa-before-release.md: 移管先 issue の未チェック項目の消化確認は同ルールがリリース前ゲートの一部として定める。本ルールはゲートを定義しない
- human-qa-checklist skill: リリース前にまとまった人間 QA を依頼する時は同 skill を使い、その項目設計に移管済み項目を取り込んでよい (二重の issue を新設しない)
- run-qa / setup-qa skill: 上の 1 に当たる項目は run-qa の対象として実装 issue 内で完遂する
- commit-create-pr skill の `## 人間が確認` の基準と jev-check skill の `check-human-verification.sh`: PR body のチェックリストに agent が確認できる項目を置かない判定は同 skill が持つ。本ルールは移管先 issue へ回す項目の判定を定め、「agent が確認できるものは人間に回さない」の向きは同じ
- ~/.claude/documents/rules/fable-task-orchestration.md: 上の 1 を作業者に出す時の実行先・指示書・監査は同ルールに従う。本ルールは実行先を定めない
